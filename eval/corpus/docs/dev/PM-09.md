# 장애 회고: DB 부하로 거래소 응답이 늦어진 사건

작성: 인프라운영팀 / 작성일: 2026-10-15

## 사건 개요

거래소 응답이 느려지거나 끊기는 장애가 발생했다. 이 증상에서 원인 후보는 여러 가지이고, DB 부하는 그중 가능성이 중간쯤 되는 후보다. 가장 흔한 원인은 아니지만 배제할 수도 없어서 초기에 후보로 올려 두고 확인했다. 확인 결과 실제 원인은 DB 부하였다.

## 타임라인

먼저 거래소 응답 지연이 보고되었다. 인프라팀은 원인 후보를 정리하면서 DB 부하를 그중 하나로 두고, 해당 여부를 가리기 위해 지표를 조회했다. 조회 결과가 DB 부하 쪽을 가리키자 이를 원인으로 판단했다. 이어서 긴급 공지, 긴급 점검, 원인 수정과 반영 절차를 차례로 열었다.

## 확인한 근거

DB 부하 여부는 자원·네트워크 지표를 조회해서 확인한다. 원인이 DB 부하라면 DB의 자원(부하) 지표가 한계에 가깝거나 한계를 넘은 상태로 나타난다. 이번에도 조회한 DB의 자원 지표가 그 상태였고, 이것을 판단의 근거로 삼았다.

## 원인

DB 부하는 DB의 운영 쪽 문제로 분류된다. 이번 거래소 지연도 DB가 처리할 수 있는 한계 근처까지 부하를 받으면서 생긴 것으로 정리했다. 참고로 DB는 서버 인프라에 의존한다. 서버 인프라에 문제가 생기면 DB에도 영향이 가는 구조이므로, DB 지표가 나빠졌을 때는 이 의존 관계도 함께 염두에 두어야 한다.

## 담당

DB의 운영은 인프라팀이 맡고 있다. 원인 확인과 절차 진행도 인프라팀이 중심이 되어 처리했다.

## 조치

원인이 DB 부하로 확인된 뒤 세 가지 절차를 열었다.

- 긴급 공지: 거래소 지연 사실을 이용자에게 알리는 절차다.
- 긴급 점검: DB 상태를 직접 살펴보고 필요한 작업을 하는 절차다.
- 원인 수정과 반영: 부하를 만든 원인을 고쳐 서비스에 적용하는 절차다.

## 재발 방지

거래소 장애 증상이 들어오면 DB 부하를 후보에서 빼지 않고, 자원·네트워크 지표부터 조회해 DB 지표가 한계에 가까운지 먼저 확인한다. DB 지표가 나쁠 때는 DB 자체뿐 아니라 그 아래의 서버 인프라 상태도 함께 살펴본다. 이 순서를 인프라팀 초기 대응 절차에 반영해 두기로 했다.
